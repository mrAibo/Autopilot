# Спецификация: журнал прогона и дыры хука (R22, R22a–R22c)

## Задача
Сборка не оставляет данных, по которым видно, куда уходят время и токены (фазы, повторы, простои, тесты), поэтому R23–R27 нечем проверять. Хук `git` из волны 1 пропускает несколько способов затереть чужие правки. Сбой Bash-хука молча блокирует все команды, и это нигде не описано. После `accept-edit` сданный таск с неосвобождённым worktree проходит публикацию.

## Решение
Одна строка на требование — что получает пользователь (глубина strict: только то, без чего требование не работает).

- **R22, R22d–R22h** — `.autopilot/run-log.jsonl`: по строке на событие — фазы (старт и конец), таски (старт, повтор, причина падения, результат шлюза), запуски тестов (число и секунды), сбросы статуса и шлюза с причиной, исполнители (роль, число ходов, токены из транскрипта субагента автоматически). Ход Autopilot не меняется. → T01
- **R22j** — в журнале только метаданные: нет текстов промптов, содержимого файлов, путей машины. Проверка вида `test_no_machine_data` покрывает журнал. → T01
- **R22k** — журнал только пишет: сбой записи или разбора не останавливает ни команду `ap.py`, ни хук. Он вне `state.js`, отпечатков и подписанных гейтов; при размере больше 1 МБ старая часть уходит в `run-log.1.jsonl`. → T01
- **R22l, R22m** — `ap.py report-run` печатает таблицу: фазы, таски, повторы, простои, токены; `--share` — сводка без данных проекта (без имён прогона и тасков, без абсолютных времён). → T01
- **R22n** — тесты T01: запись на каждом событии, сбой записи не ломает прогон, нет путей машины и текста промптов, сброс статуса попадает в журнал с причиной. → T01
- **R22a, R22o** — хук строгого прогона отклоняет `git.exe stash`, `/usr/bin/git stash`, `bash -c "git stash"`, `git restore .`, `git checkout .`, `git clean -fd`; `git commit --only`, `git status`, `git diff` и слово `stash` в кавычках или в сообщении коммита проходят. → T02
- **R22b** — `docs/autopilot/claude-code.md`: что делает `onFailure: block` на хуке `Bash` при сбое хука и как снять (удалить запись из `.claude/settings.json`); поведение хука не меняется. → T03
- **R22c, R22p** — после `accept-edit` сданный таск с неосвобождённым worktree не проходит публикацию: отказ с командой, как worktree посадить (`worktree NN land`) или снять (`worktree NN release`); тест на этот случай; тест `test_changed_ticket_resets_previous_acceptance` получает имя по своей проверке (сданный таск не сбрасывается молча, а останавливает публикацию). → T03

## Решения по реализации
- Журнал — один файл на проект, а не на прогон: строки несут поле `run`, чтобы сравнивать прогоны (нужно для R23–R27). Он не коммитится (`.gitignore`), как `serve.*`: это локальная диагностика, а не запись об обещанном.
- Запись встаёт в `log()` — единую воронку `ap.py`, — а не в каждую команду: одно место, нельзя забыть событие. Недостающие события (`ticket-reset`, ожидание, длительность тестов) добавляются там, где они случаются.
- Токены считаются на `SubagentStop` в `claude_attest.py` из `agent_transcript_path`, а не при построении отчёта: транскрипт позже может исчезнуть. Чтение ограничено 5 МБ, ошибки глотаются.
- Отдельный модуль `run_log.py` с `append` без исключений: и `ap.py`, и хук зовут одно и то же.
- Хук `git`: имя команды сравнивается по имени файла (`git`, `git.exe`, любой регистр); `restore` блокируется при аргументе `.` вместе с `--staged` тоже: он трогает общий индекс. `bash -c` разбирается рекурсивно до глубины 3; `$(...)`, `eval`, скрипты по-прежнему не разбираются — предел хука остаётся записанным в docs.
- Ротация — одна запись: при размере больше 1 МБ файл переименовывается в `run-log.1.jsonl` поверх прежнего.
- `ASSUMPTION`: журнал по умолчанию включён и не отключается переменной — бриф говорит «по умолчанию» и «только пишет».
- `ASSUMPTION`: `report-run --share` печатает идентификаторы тасков только как порядковые числа и роль исполнителя как `executor`/`reviewer`/…, потому что названия профилей содержат слаг прогона.
