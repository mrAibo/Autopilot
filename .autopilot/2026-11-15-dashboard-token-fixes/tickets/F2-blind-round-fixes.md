## Что должно заработать

Токен печатает только `ap.py url`, и никакая другая форма вызова, включая голый `ap.py`; одновременный запуск `ensure_key()` при старом пустом `gate.key` даёт один ключ и ни один процесс не падает.

## Из брифа, дословно

> «Адрес с `?t=` печатается при каждой команде `ap.py`, а в `AGENTS.md` мы просим не вставлять его в чат.»
> «Ключ `gate.key` создаётся не атомарно.»

## Критерии приёмки

- [ ] Голый `ap.py` (без команды) печатает адрес без `?t=`; только `ap.py url` печатает адрес с токеном; `serve(state, with_token=...)` больше нигде не получает `True` для обычной команды; `--help` и `AGENTS.md` (таблица команд) и `phases/0-instruments.md` говорят «адрес с токеном — `ap.py url`»; тесты, закреплявшие обратное (`test_only_the_bare_command_asks_serve_for_the_token` и т. п.), обновлены по смыслу
- [ ] Старый пустой `gate.key` и одновременный `ensure_key()` (не меньше 8 процессов по 4 потока, на Windows тоже): все читают один и тот же ключ, ни один процесс не падает (`PermissionError` от `os.replace` и подобное исключено), файл ни разу не пуст у читателя после возврата; приём — переименовать пустой файл во временное «осиротевшее» имя (выигрывает один процесс, остальные получают `FileNotFoundError`) и создавать ключ тем же `link`-путём, что и для нового файла, проигравший читает ключ победителя; временные файлы убираются; тест на процессах это воспроизводит и падает на текущем коде
- [ ] `DpapiKeyTests`, `tests/test_followups_key.py`, `tests/test_followups_token.py`, `tests/test_ap_audit.py` зелёные
