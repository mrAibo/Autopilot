# Спецификация: идеи из purpleflow, волны 1–4 (R22–R27)

## Задача

Разработчик Autopilot хочет, чтобы ревью и приёмка видели невыполненное из плана и не пропускали рискованное, чтобы вид работы (баг, рефакторинг) менял правила проверки, чтобы влитие не вставало на чужом красном, чтобы сборка шла быстрее и помнила уроки прошлых сборок — и чтобы ничего из шлюзов, слепой приёмки, подписей, guard, правил Opus и Fable при этом не ослабло.

## Решение

Поверх существующего потока добавляется шесть узких кусков. Всё новое: код — в **новых модулях** `skills/autopilot/tools/` (в `ap.py` только разбор команды и вызов), тексты — в **новых файлах** `phases/` и `prompts/` (обычный путь не растёт сверх порога `test_text_split.py`).

| Волна | Что появляется |
|---|---|
| 1 | `ap.py plan-fact` (план → факт, поле `planFact`, строка «план: N из M»); чек-лист рисков ревью ветки; второй проход по блокирующим (`blocker confirm`); `agent-for` работает в обычном прогоне; проверка обхода замечаний (`check-bypass`) |
| 2 | ось `kind` (`quick`/`bug`/`task`/`refactor`); отказ `land` при не красном тесте бага и при правке старых тестов в рефакторинге; проверка перед влитием (`land_check`), `--include` для чужих новых файлов |
| 3 | сводный возврат исполнителю (`ticket NN bundle`), сторож молчания (`ap.py silence`), копия зависимостей в worktree |
| 4 | `.autopilot/lessons.md` и `.autopilot/profile.md`, команды `ap.py lessons`/`profile`, чтение при `init` |

## Решения по реализации

- **Код в новых модулях** (`plan_items.py`, `review_checks.py`, `land_check.py`, `silence.py`, `lessons.py`, `kinds.py`), `ap.py` лишь вызывает: ap.py уже ≈4600 строк и общий для всех тасков. *Почему:* параллельные правки одного файла ломают влитие, а харнессы тестов копируют ограниченный набор файлов.
- **Состояние** — только через `state_io`; новые поля (`planFact`, `kind`, `tk["startHead"]`, `tk["redproof"]`, `lessonsRev`) необязательны; чтение старого `state.js` без них не падает.
- **Агенты запускает оркестратор**, не `ap.py`: инструмент считает, печатает и отказывает; текст в `phases/`/`prompts/` говорит оркестратору, кого позвать.
- **Вид `bug` и красное доказательство:** воспроизводящий таск вливается без полной проверки (тест красный по замыслу), все остальные таски `bug`-сборки вливаются только после его `done`.
- **Номер ADR:** 0015 закреплён за R33 в «Договорились» прошлой сборки, поэтому решение по видам работ — `docs/adr/0020-work-kinds.md` (вместо названного в R24g `0015`); отмечено в отчёте.
- **Влитие в подпапке репозитория не поддержано** (как в `PROGRESS.md`): проверка пропускается с предупреждением.
- **Порядок:** шесть тасков идут по очереди (общий `ap.py` и `prompts/`): R22 → R23(+G02) → R25(+G01) → R24 → R26 → R27 → документация. Причина обмена R24/R25: `land` меняют оба; R25 даёт базу проверок, R24 вешает свои отказы на неё.

## Вне рамок

| Требование | Почему не сейчас |
|---|---|
| R28 (R28a–d) | пользователь: «R28 не трогай» |
| Замер доли снятых блокирующих (R23f), замер «до/после» (R26d) | журналы прошлых сборок не хранят нужного; записывается как не измеренное |
| Копия зависимостей на Windows | требование оставляет прежний путь (записывается в доке) |
| Выпуск отдельными релизами по волнам | пользователь велел собрать волны 1–4 одной сборкой; сборка укладывается в ~6 тыс. строк |
| `ticket NN review` блокирует зависимого (пункт 3 прошлых остатков) | пользователь не взял |
