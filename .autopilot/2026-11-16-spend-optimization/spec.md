# Спецификация: учёт расхода и короткий вывод проверок

## Задача

«Сделай отдельную сборку по оптимизации расхода». Оптимизировать вслепую нельзя: учёт `spend` видит только входные и выходные токены субагентов. Кэш (а на нём держится цена) и главная сессия-оркестратор в него не попадают, поэтому внешнее ревью с «оркестратор жжёт 65–90%» нечем ни подтвердить, ни опровергнуть. Плюс исполнители читают лишний вывод проверок.

## Решение

После сборки `report-run` и «Подробности» дашборда показывают, сколько токенов ушло на чтение и запись кэша и какая доля входа пришла из кэша — по ролям, моделям и таскам. Строка «оркестратор» показывает расход главной сессии за время прогона. Исполнитель по умолчанию запускает проверки с коротким выводом. Честно: уменьшает расход только это последнее; остальное — учёт, без которого дальнейшие оптимизации вслепую.

## Истории (T0: короткая спецификация, приёмка в таске)

- **R01** Учёт кэша субагентов.
  - R01.1 `compute_spend` по каждому ключу (`byRole`, `byModel`, `byTicket`) считает ещё `cache_read` и `cache_write`; `tokens` остаётся «вход + выход» (старые панели не меняются).
  - R01.2 Доля попаданий `hit` = `cache_read / (input + cache_read + cache_write)`, целое число процентов, `null`, если знаменателя нет.
  - R01.3 Строка журнала без полей кэша, с `True`, отрицательным или нечисловым значением даёт 0, не исключение.
  - R01.4 `report-run` печатает под таблицей токенов таблицу «Кэш по ролям»: роль, чтение, запись, доля попаданий. `--share` — те же числа без имён.
  - R01.5 Без `--share` та же таблица есть и по профилям (`agent_type`): по ней видно, держится ли общий кэш у исполнителей разных тасков (пункт 2 ревью: «не мешает ли общему кэшу префикс исполнителей»). Это замер, не правка профилей; вывод по нему — в отчёте сборки.
- **R02** Учёт оркестратора.
  - R02.1 `run_log.usage_by_model(path, since, until=None)` читает JSONL-журнал главной сессии построчно (без лимита размера) и возвращает `{модель: {turns, input, output, cache_read, cache_write}}` по ответам ассистента, у которых `timestamp` не раньше `since`; строки с `isSidechain: true`, без `usage`, повторы одного `message.id` (берётся последний) и испорченные строки пропускаются; нечитаемый файл — `None`.
  - R02.2 `ap.py spend-orchestrator [--transcript PATH]` пишет в `run-log.jsonl` по строке на модель: `k=executor`, `role=orchestrator`, `run`, `model`, `turns`, `input`, `output`, `cache_read`, `cache_write` — только числа и имя модели, без текста разговора. Без `--transcript` путь берётся из `~/.claude/projects/<имя папки проекта>/`, самый свежий `*.jsonl` (имя папки: все символы кроме латиницы и цифр заменены на `-`; корень `~/.claude` меняет `CLAUDE_CONFIG_DIR`).
  - R02.3 Повторный вызов не удваивает расход: `compute_spend` берёт из строк `role=orchestrator` последнюю на модель.
  - R02.4 `ap.py finish` вызывает то же самое в конце и печатает одну строку; нет журнала, ошибка чтения, нет модели — одна строка «расход оркестратора не найден: …», `finish` не падает и не меняет результат.
  - R02.5 `since` — `startedAt` прогона; `until` — «сейчас».
  - R02.6 Роль `orchestrator` входит в `byRole` и `byModel`; в `byTicket` её нет.
- **R03** `prompts/executor.md` в «Ритм проверок» получает правило: по ходу запускать проверки в тихом режиме и читать только итоговую строку, хвост лога и упавшие тесты; полный лог читать, только если красное. Правило про код выхода (`pipefail`) остаётся.
- **R06i** Дашборд: в таблицах «Расход» (`byRole`, `byModel`, `byTicket`) появляется колонка «Кэш, %» (доля попаданий; «—», если `null`); русский и английский тексты. В шапке карточки — число токенов как раньше. В `docs/autopilot/measuring-cost.md` — раздел, как читать новые числа и чего они не говорят; `AGENTS.md` — одна строка.

## Решения по реализации

- Оркестратор пишется в уже существующий вид строки `executor` с полем `role`: схема журнала, `summarize` и `report-run` не получают нового вида.
- `usage_by_model` читает файл построчно, потому что журнал главной сессии бывает десятки мегабайт, а `usage_from_transcript` ограничен 5 МБ и читает всё в память.
- Разрешение пользователя — читать только суммы токенов: поля `model`, `id`, `timestamp`, `isSidechain` нужны лишь для отбора и группировки, а сохраняются суммы и имя модели.
- Читаются только поля `type`/`message.role`, `message.model`, `message.id`, `message.usage`, `timestamp`, `isSidechain`; текст сообщений не разбирается и нигде не сохраняется.
- Путь к журналу сессии не берётся из хука подписанных свидетельств: это меняло бы подписанные строки гейтов. Догадка по самому свежему файлу — осознанный компромисс (`shortcut`: две сессии в одной папке — берётся та, что писала последней; `--transcript` задаёт путь вручную).
- Только стандартная библиотека.
