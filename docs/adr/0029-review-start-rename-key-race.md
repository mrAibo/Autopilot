# 0029. Старт зависимого при `review`, переименование в `commit_paths`, гонка ключа подписи

Статус: принято (2026-11-20).

## Старт зависимого при `review`

- `ticket NN review` ставят после коммита (`phases/6-review.md`): код зависимости уже в `HEAD`. Поэтому `ticket MM start` допускает зависимости в `done` и в `review`; `ticket MM done` по-прежнему ждёт `done`, и `ticket MM land` не менялся (`waiting` в `cmd_land`). Зависимость в `pending`, `in-progress`, `repair`, `failed` — отказ «сначала заверши зависимости».
- Незакрытый `BLOCKING` не пропускает сборку: зависимый не сдаётся, пока предшественник не `done`.
- Не менялось: `scheduler.py` считает зависимость вне `done` незавершённой (вне зоны этого таска), поэтому `schedule` такой таск не предложит, хотя `ticket MM start` его пускает.

## `commit_paths` и переименование

- `git mv old new` ставит в индекс `D old` и `A new`; `git commit --only -- new` уносил только `new`, и `D old` оставался в индексе после коммита. `land` и `chore` берут пути из `git status --porcelain`, а там у переименования только новый путь.
- Теперь `commit_paths` читает `git diff --cached --name-status -M -z` (без путей: с ними переименование выглядело бы как `A new`) и добавляет прежний путь каждого `R`, чей новый путь есть в `paths`. Сигнатура и поведение для остальных путей прежние; чужое переименование в индексе не трогается.
- Побочно: проверка «нечего коммитить» (`git diff --cached --quiet`) печатала заголовок переименования в вывод; теперь её вывод перехвачен.
- Не менялось: если в `paths` одновременно оба пути переименования, `git add -- old` падал и раньше (пути берутся из `porcelain`, там только новый).

## Гонка `gate_sign` в параллельном прогоне

Воспроизведено: 5 кругов по 20 одновременных `python -m unittest tests.test_gate_sign` на прежнем коде — `test_threads_racing_over_an_old_empty_key_end_up_with_one_whole_key` упал в 6 запусках из 100 (`2 != 1`); без нагрузки одиночный процесс не падал (600 кругов). 16 процессов по 200 гонок из 8 потоков на старом пустом `gate.key`: около 1,3 % кругов с `OSError` «ключ подписи не читается» и около 3,4 % с двумя разными ключами.

Причина в коде `gate_sign`, не в тесте: `_claim_empty` переименовывал `gate.key` в сторону, не зная, пуст ли он.

1. Гонщик с устаревшим «файл пуст» уносил уже записанный полный ключ и возвращал его через `os.link`. Пока пути не было, третий гонщик создавал свой ключ, возврат падал с `FileExistsError` (проглатывался), и первый ключ терялся, хотя его уже прочитали и вернули: два разных ключа в одном `ensure_key`.
2. В тот же миг читатель получал `PermissionError` на `gate.key` (Windows не даёт открыть переименуваемый файл); `_stored_key` читал его как «ключ не читается», и `ensure_key` падал с `OSError` (все 42 ошибки на 3200 кругов — `PermissionError` при чтении).

Изменено:

- `_claim_empty` берёт заявку жёсткой ссылкой `gate.key.claim` на сам файл (атомарно, без перезаписи) и проверяет размер уже под заявкой: полный ключ не двигается, заявка снимается. Пустой файл удаляет только владелец заявки; остальные ждут ключ, как и раньше. На согласование `sleep` не нужен; повтор при занятом читателем файле — `_retry_busy` (как `state_io.replace_with_retry`).
- Отдельная хрупкость, найденная при поиске: `_dpapi` (Windows) на каждом вызове создаёт класс `Blob` и перезаписывает `argtypes` общих функций `crypt32`/`kernel32`; два потока вперемешку получали `ArgumentError: expected LP_Blob instance` (при `sys.setswitchinterval(1e-6)` — 828 вызовов из 2400). На наблюдавшиеся падения она не влияла (при одной только правке 1 — 0 ошибок на 3200 кругов), но превращала бы параллельный вызов в «ключ не читается»; вызов теперь идёт под `threading.Lock`.
- После правки: 3200 гонок (16 процессов по 200) — ни одной ошибки и ни одного расхождения ключей; 5 кругов по 20 параллельных запусков `tests/test_gate_sign.py` (100 запусков) зелёные.

Правка по код-ревью ветки (F1):

- Заявка `gate.key.claim` снималась в `finally` без `_retry_busy`: на Windows читатель, державший её открытой, давал сырой `PermissionError` из `ensure_key`, а заявка оставалась. Теперь удаление идёт через `_retry_busy`; если читатель не отпустил и после повторов — `OSError` с именем файла заявки и словами «удали её вручную», ключ не трогается.
- Ошибка «файл остался пустым или занят» теперь называет `gate.key.claim` и говорит, что заявку убитого процесса можно удалить.
- Тест «третий гонщик в середине заявки» проверяет результат (оба гонщика читают один и тот же ключ, ключ на месте), а не вызовы `os.link`/`os.rename`: третий гонщик запускается на первом же изменении каталога любым вызовом.

Осознанно не сделано:

- `PermissionError` при чтении ключа в миг замены файла (`_write_key_file` для старого обычного ключа, Windows) по-прежнему читается как «не читается»: повтор чтения не добавлялся, в замерах не встретился.
- Владелец заявки, убитый между созданием `gate.key.claim` и удалением пустого `gate.key` (микросекунды), оставит заявку, и `ensure_key` ответит «файл остался пустым или занят; если рядом лежит …gate.key.claim от убитого процесса, удали её» (выход — удалить `gate.key.claim`). Пустой `gate.key` теперь возможен только от очень старых версий.
- Тома без жёстких ссылок: `os.link` в заявке поднимет `OSError` вместо прежнего переименования.
