## Контекст
Профиль `cheap` был один и означал `haiku/low` и для разведчика, и для исполнителя механического таска (I11, `DEFAULT_POLICY`). Аудит указал, что для кода нужен Haiku на высоком effort, а не на низком (R23).

## Решение
Профиль `cheap` делится на два: `cheap_read` (`haiku/low`) для разведчика и `cheap_code` (`haiku/high`) для исполнителя механического таска. Хост-ёмкости в `model-capabilities.json` допускают `haiku/high`. Запрет Fable и запрет Opus без подтверждения пользователя не меняются.

## Почему
- Оставить один `cheap` на `haiku/low` отвергнуто: исполнитель кода остаётся на низком effort, который аудит назвал слабым для кода.
- Поднять весь `cheap` до `haiku/high` отвергнуто: разведчик много читает, и высокий effort платится за чтение, а не за код. Разделение сохраняет дешёвое чтение.

## Последствия
- Появились два имени профиля. Всё, что перечисляет профили (`plan-models`, `report-run` по моделям, тесты роутера), должно знать `cheap_read` и `cheap_code`. Как сохранённые маршруты и политики со старым именем `cheap` ведут себя сейчас, по коду не проверено. Проверить перед сдачей.
- Расход исполнителя растёт: `haiku/high` тратит больше токенов на таск, чем `haiku/low`. Замер даёт `report-run` по моделям (R26). Пробной сборки не было, цифр нет.
- `model-capabilities.json` — файл хоста. При обновлении через `upgrade-tools` его нужно копировать в проекты, иначе `haiku/high` не будет допущен.
- Правила «Fable не проходит никогда» и «Opus только с подтверждением» не изменены, но тесты роутера должны проверять оба случая.
