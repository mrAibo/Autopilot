# Phase 5 — Build (digest)

Working digest of `phases/5-subagents.md`. **Read the full text only if something below is not enough** (the executor-inputs table, the legacy shared-tree mode, the dependency rule in detail).

`ap.py stage build`. Identical in all four modes, hands-free. Claude Code host: also the digest `short/5-host-claude.md`; **Codex host: read `phases/5-host-codex.md`**. `--sequential-host` → `5-sequential-host.md`; strict routing / isolated tickets / host controller → `5-strict.md` before the first ticket.

- **One ticket, one subagent, one fresh context; never two tickets in one context.** **You dispatch, you do not build** (rule 5): your keyboard reaches `.autopilot/**`, the memory files, `.gitignore`, `.env.example` and git (`add`, `commit`, `status`, `--stat` — never the diff). "Две строки, сделаю сам" is exactly what this forbids.
- **The executor gets paths, not contents:** `prompts/executor.md` (by `skillDir`, required before the first edit), its ticket, spec sections by path + headings, `interfaces.md`, `notes.md`, `context-pack.md`, `reference.md` if the user will look at it, the check command, its zone and the zones beside it, credential **names** only. Ordinary Claude Code: `autopilot-executor` with the ticket's `model` and `effort` **in every call** (the profile has neither). Rules the executor must follow travel in its prompt or `prompts/executor.md`. Models: OpenAI default Luna for cheap/balanced, Sol for strong; Anthropic default Haiku for cheap, Sonnet for balanced/strong; Astra/Fable never; the main session's model never leaks into subagents; no verified capabilities → stop delegation and report the blocker. Haiku red after first retry → `ticket NN retry --cause tests --escalate` (once); missing deps/access/ambiguity is not a model-strength failure.
- **Dependencies:** ticket 01 installs everything «Решения по реализации» names; a later `BLOCKED` with a name that fits a made decision → add it to «Решения», relaunch with permission to install exactly that.
- **Waves:** before each, `python .autopilot/ap.py schedule --max-parallel 2`; follow `selected[]` actions (it spawns nothing); never launch what `blocked[]` lists. **Launch a whole wave in one message**, one background subagent call per ticket. At most two in flight (three only if verified policy allows and truly independent). Zones disjoint, doubt → serialise. A wave is not a barrier: when one returns, launch the next ready ticket first, then process the landed one. A dependent never launches on an uncommitted parent (a parent in `review` is committed: `start` passes, `done` waits for the parent's `done`; isolated run: the parent must be `done`). `ap.py ticket 02 03 start` goes **before** the launch, in the same message as the Agent calls. **One event, one message** (mark + commit + next launch + line to user together). Waiting = ending your turn.
- **Return contract** (`prompts/executor.md` «Что вернуть»): `STATUS: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT`, `FILES`, `TESTS`, `REDPROOF`, `INTERFACES`, `REQUIREMENTS`, `COMMIT`, `CONCERNS`, `BLOCKERS`. **Hard cap 15 lines / 1,200 characters**, no code, no diffs; a longer block is not read — ask again in one line.
- **After each ticket, in order:** (1) read the contract; none → ask for it; `BLOCKED`/`NEEDS_CONTEXT`/a CONCERNS line saying the plan does not hold → `phases/5-repair.md` now (two `NEEDS_CONTEXT` in a run = tickets too thin). (2) Append its `INTERFACES` to `interfaces.md` yourself; two claims on one interface = plan defect. (3) **Land:** `python3 .autopilot/ap.py ticket 03 land --message "T03: …" --requirements R01,R02` (zone check, the ticket's «Целевая проверка» if it has one, else «Полная проверка» — the full one then runs on `stage review` and in `finish`; one commit of the zone with `Autopilot-Run`/`Requirements` trailers, then `done`; `--zone a/,b/`, `--allow path`, `--include a,b`, `--placeholder R05`; success ≤5 lines; compare its test count with the contract — a `DONE` with new criteria and no tests is a дозапрос; red = exit 2, no commit, a stray file → дозапрос, red → `5-repair.md`, you repair nothing; isolated run keeps `worktree NN verify/finalize/land`, then `ticket NN done`). (4) `Ревью: да` or a requirement reported not done → `ap.py ticket NN review`, reviewer in the background, go on (`6-review.md`); its `BLOCKING` lines go to `phases/5-repair.md`. (5) Ledger: stubs → `add debt.placeholders`, new variables → `add debt.emptyEnv NAME`, `A##` in code → `add additions`, craft concerns → `add concerns`; project memory only for a real discovery (`9-memory.md` Moment 2). (6) One plain line to the user: «Бот принимает заявки — 3 из 8 готово».
- Two tickets returning together are processed one at a time, each through the whole list.
- **Build over:** every ticket `done` (or `failed` with dependents named as waiting), no point review running → `ap.py stage review` and `6-review.md`.
