# Phase 6 — Review (digest)

Working digest of `phases/6-review.md`. **Read the full text only if something below is not enough** (the exact list of what blocks, the F1 ticket recipe, Opus-reviewer rules).

Two moments, both by someone who did not write the code: **point review** (tickets with `Ревью: да`, or a ticket whose contract reports its own requirement as not done; after the commit, never before; none at T0) and the **whole-branch review** (once, always, every tier and mode). Three axes reported separately: **Manifest** (the user's words delivered?), **Spec** (what the spec decided), **Craft** (fit to build on). Which axis: could the executor have known? Yes → Spec/Craft, fixed in this ticket; no → Manifest, the defect is in the spec or the cut — repair those first.

Reviewers, the coverage reader and explorers run only on a verified, permitted model; Astra/Fable never automatically.

**Point review:** one fresh subagent per review, route by `model_router.py` (never inherit the orchestrator model; blocked route = no spawn). Ordinary run `autopilot-reviewer` with `model`+`effort`; strict `roleAgents.reviewer`. Launch in the background right after the commit: `ap.py ticket NN review`, then go on — never hold a wave for it. It gets by path `prompts/review.md` (required before the diff), the ticket file, the named spec sections, `interfaces.md`, the repo conventions; pasted: the executor's `TESTS`/`REDPROOF` and **why it is reviewed**; plus `git show <commit>`. It must not repair, refactor, invoke skills or spawn agents. Verdict per axis + a `BLOCKING` line. Nothing blocking → `ap.py ticket NN done` again. `BLOCKING` → `5-repair.md` verbatim (`ticket NN repair --note` opens a blocker resolved only after independent re-review). `FINDINGS` → `ap.py add concerns "…"` with file and line. A blocking fix that changes an interface in flight → append to `interfaces.md`, one line to each affected executor before its commit. **Re-review of a repair** (mode «ремонт»): fresh subagent, at most once per ticket, gets `git diff <ticket commit>..<repair commit> -- <zone>` and the conditions to close.

**What blocks (only the reviewer's `BLOCKING` line triggers a repair):** Manifest `partial`/`missing` · an invented fact · Spec *extra* surface · a red check or a test bound to internals · in the foundation a defect later tickets build on · for a risky ticket a hole in that risk. Everything else waits for the branch review. **You never widen the list** — widening is a line to the user with its price.

**Whole-branch review** (`ap.py stage review`): one fresh `autopilot-reviewer` (T3 with a large diff: up to three, a group of zones each); Opus reviewer only via `ap.py agent-for reviewer --diff-lines N` (role approved + diff > 3000). It gets `prompts/review.md` (mode «ветка»), the range `git diff <baseCommit>..HEAD`, `spec.md`, `interfaces.md`, repo conventions, and `state.js` → `concerns` to confirm or drop. Manifest axis is not judged here (G4 does). Returns findings as **fix now** (bounded, costs more to leave) / **report** / **drop**; repeated across ≥3 tickets = fix now; security = fix now or report, never drop. Explicit `BLOCKING` → `ap.py blocker open --note "…"` (or `ticket NN repair --note`); every `BLOCKING` goes to a second pass with `prompts/confirm.md`; a fix-now is not resolved because its ticket says done. Follows `prompts/review-checklist.md` (plan items → `ap.py plan-fact`, six risk points → `ap.py check-review-report`).

**All fix-now findings become one ticket `F1`:** `tickets/F1-<slug>.md`, requirements the fixed code serves, `Зависит от: —`, wave after the last, zone = union of the files named, `Ревью: да — ремонт ветки`, `Модель: сильная`, findings verbatim as criteria; `ap.py tickets`; one executor (strict: `ticket F1 route` → repair executor; ordinary: `autopilot-executor` + `ticket F1 route --model … --effort … --reason "…"`), the check, one re-review «ремонт» (what is still open goes to the report, no second round), one commit — never by you or the reviewer. Nonblocking → `ap.py add report "…"` in words the user understands. An unresolved BLOCKING stays open in the ledger; no final acceptance until genuinely resolved. Then `phases/8-final.md`. To the user: one line after the branch review, «Код-ревью: нашлось 7 замечаний, 4 поправил, 3 — в отчёте», nothing per ticket.
