# Бриф — Autopilot 2.3: надёжность, адаптивные модели и Dashboard 3.0

Дата: 2026-10-25
Репозиторий: https://github.com/mrAibo/Autopilot
Базовая версия: 2.2.0 (`25b5fbada50742f1b6a900a5a92800759e5c74d4`)
Ветка реализации: `feat/autopilot-2.3-adaptive-router-dashboard`

## 1. Цель

Развить Autopilot в надёжный, прозрачный и экономный автономный фреймворк разработки, совместимый с ChatGPT/Codex (OpenAI) и Claude Code (Anthropic). Избежать появления дорогих субагентов без разрешения владельца. Улучшить интерфейс Dashboard: современный, понятный, информативный, адаптивный, без лишних зависимостей.

Сохраняется базовая последовательность: brief → manifest → briefing → spec → plan → build → review → acceptance; сохраняется трассировка требований до коммитов и независимая приёмка.

## 2. Требования и критерии приёмки

### R01. Строгая сдача и объективное состояние

- Команда `finish` должна отказать при незавершённых тасках, failed tests, отсутствующих/отрицательных G1–G4, незакрытых блокирующих замечаниях; никаких ложных «сдан».
- Запись `ticket done` должна требовать существующего коммита в HEAD, успешной проверки и валидного жизненного цикла. Повторные попытки, откаты и review не должны оставлять требование ложно `done`.
- После `reopen`/изменения ticket определять устаревшее принятие по содержимому и сбрасывать его.
- Пустой/отсутствующий манифест и пустой план не проходят G3.
- G2/G4 должны проверять согласованность чисел и списка несоответствий.
- Учитывать совместимость со старыми состояниями и документировать миграцию.

### R02. Безопасная работа

- Атомарные записи состояния и межпроцессная блокировка; защита от одновременного изменения одной сборки.
- Строгая валидация slug, путей, ID и состояния; запрет выхода за каталог прогона.
- Не допускать убийства чужого/нового dashboard-сервера устаревшим stopper; проверять идентификатор процесса/сессии.
- Надёжно считывать exit code тестов, не теряя его через пайп в `tail`.
- Ограничивать внешние действия; не писать секреты и персональные значения.

### R03. Адаптивный маршрутизатор моделей

- Оценка задачи перед запуском по нескольким факторам: сложность, связность, неопределённость, контекст, тестируемость и риск.
- Настройка модели, Effort, делегирования, числа параллельных агентов, бюджета и стратегии эскалации в отдельном прозрачном policy/config.
- Отдельные адаптеры OpenAI/Codex и Anthropic/Claude Code; алиасы моделей разрешать по реальным возможностям harness, не считать названия универсальными идентификаторами.
- В режиме по умолчанию запрещены дорогостоящие Astra/Fable как субагенты; Opus разрешать только по явной политике и ограничениям. Выбранная модель оркестратора не наследуется автоматически исполнителем.
- Простые тексты/документация → дешёвая модель и низкий Effort; обычный код → доступная средняя модель; сложные/рискованные изменения → более сильная модель и независимая проверка.
- При отсутствии механизма выбора модели работать в безопасном режиме: не делать вид, что запрет был обеспечен; выбирать остановку делегирования или явную политику fallback.
- Retry классифицировать: ошибка окружения/прав/контекста не требует эскалации; сложная логика может эскалироваться в пределах бюджета.
- Каждый таск должен содержать reason выбора; отсутствие возможностей среды не замалчивать.

### R04. Dashboard 3.0 — обязательный редизайн

- Современный визуальный стиль, улучшенная типографика, более спокойные цвета, хорошие отступы, понятная визуальная иерархия.
- «Сейчас выполняется», общий прогресс, пройденные/ожидающие этапы, таски и блокировки, тесты, gate, ошибки и следующие действия — без поисков по странице.
- Отдельные сведения о выбранной модели, провайдере, Effort, риске/сложности, retry и расходе (когда телеметрия доступна).
- Отсутствующие значения показывать как «нет данных», а не выдумывать 0 $/приблизительную стоимость.
- Responsive для узкой панели Claude Code и широкого браузера; светлая/тёмная темы, EN/RU; читаемые карточки, доступность клавиатурой, контраст.
- Без React/Vue и CDN: автономный HTML; сохранение snapshot и автоматического обновления раз в 10 секунд.
- Защита от внедрения HTML из state/brief; текст экранируется.

### R05. Документация

- Обновить README.md и README.ru.md, CHANGELOG.md, инструкции skill фаз планирования/делегирования и документацию архитектуры.
- Создать документацию выбора моделей, политики затрат и ограничений провайдеров.
- Реалистично описать, что автоматически проверяет Python, а что остаётся инструкцией агента.
- Устранить расхождения с upstream nick-vels/skills: задокументировать происхождение и схему обновлений.

### R06. Регрессии и измерения

- Расширить unittest, добавить негативные сценарии finish, invalid model, reset/reopen, гонки и ошибочные номера тестов.
- Автоматическая проверка CI для Python (как минимум Linux/Windows), синтаксис и тесты.
- Сравнение версий на одном benchmark: токены/затраты при доступности, число исполнителей, исправления, длительность, процент успешной приёмки. Не выдавать нормализованные токены за реальные деньги.

## 3. Политика по умолчанию

- Провайдер определяется рабочей средой: OpenAI Codex → OpenAI; Claude Code → Anthropic.
- Уровни: cheap / balanced / strong / restricted; реальные имена моделей подставляются адаптерами из доступной конфигурации.
- Restricted модели не запускаются автоматически.
- Максимум одновременно работающих исполнителей: 2, до 3 только при выгоде и разных зонах.
- Никакого самопроизвольного повышения на дорогую модель; при неопределённости нужна остановка или разрешение.
- Отдельный «экономичный» и «качественный» профили допустимы, но оба подчинены запрету restricted.

## 4. Область работ и порядок

1. P0: проверяемые ошибки state/finish/gates, regression tests, CI.
2. P1: маршрутизатор выбора моделей и обязательная проверка политики перед Agent call.
3. P1: Dashboard 3.0, информативность и оформление.
4. P1/P2: race/locks, Git, retry, telemetry, документация, бенчмарки.
5. В конце: code-review изменений, проверка совместимости, отчёт с недоделанным.

## 5. Нефункциональные ограничения

- Не переписывать весь проект; сохранить существующие сценарии CLI и совместимость по возможности.
- Не нарушать действующий `main`: изменения через отдельную ветку и pull request.
- Не использовать секреты, платные API или деплой для тестирования.
- Измерять фактическую экономию, не обещать заранее процент снижения.
- Не утверждать, что работа завершена, пока обязательные проверки реально не пройдены.

## 6. Определение «готово»

Вся команда CI зелёная; отрицательные тесты подтверждают блокировки; модельная политика исключает restricted при штатном запуске; документированы OpenAI и Anthropic; dashboard читаем на узкой и широкой ширине, оба языка/темы работают; руководство отражает реальный код. Все отклонения и отложенные пункты перечислены в PR и отчёте.
